# Flow — Warroom_GetPunchDashboardBundle

## Trigger

**Power Apps (V2)**

Inputs, in this exact order:

1. `ProjectId` — Number
2. `TemplateId` — Number

## Action 1 — Execute stored procedure (V2)

Connection: existing PULSE SQL connection.

Stored procedure:

```text
warroom.usp_GetPunchDashboardBundle
```

Parameters:

```text
ProjectId  = triggerBody()['number']
TemplateId = triggerBody()['number_1']
```

Use the dynamic input tokens generated by Power Apps rather than manually retaining the internal names when they differ.

## Action 2 — Compose

Expression:

```text
first(body('Execute_stored_procedure_(V2)')?['ResultSets']?['Table1'])?['result']
```

## Action 3 — Respond to Power Apps (V2)

Output:

```text
Name: result
Type: Text
Value: outputs('Compose')
```

## Power Apps connection name

The screen supplied in this sprint calls:

```text
Warroom_GetPunchDashboardBundle.Run(ProjectId, TemplateId)
```

The Flow must therefore be added to the app with the connection name `Warroom_GetPunchDashboardBundle`.

## Refresh Flow

Create a second Flow named `Warroom_RefreshPunchDashboard` only after validating the read Flow.

Actions:

1. Power Apps (V2): `ProjectId`, `TemplateId`, `RequestedBy`.
2. Execute `warroom.usp_GeneratePunchDashboardSnapshot`.
3. Execute `warroom.usp_GetPunchDashboardBundle`.
4. Return the `result` field using the same contract.

Do not connect the refresh Flow until the read-only load has been validated in Power Apps.
